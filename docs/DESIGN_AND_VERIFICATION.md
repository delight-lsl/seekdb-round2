# MiniVectorDB 简要设计与验证记录（对应第 4.3 节）

## 1. 记录布局与存储设计

- **数据文件即提交日志**：每张表一个 Append-only 文件 `/data/tables/t_<tid>_g<gen>.dat`。行数据只落盘一次，不再经过独立的 WAL 双写。
- **帧结构（`MVD1`）**：`magic (4B) + op (1B) + row_id (8B LE) + payload_len (4B LE) + payload + crc32 (4B LE)`。
  - `op = 1 Put`（插入或更新后的整行）、`2 Tombstone`（删除）、`3 Commit`（事务组结束符）、`4 Pending`（跨文件事务的组结束符，`row_id` 字段存事务号）。
  - 一个事务对一张表的全部修改构成一个**组**：若干 `Put`/`Tombstone` 帧 + 一个结束符帧。没有合法结束符的组视为未提交尾部。
  - 大组（≥ 16 KiB）的结束符帧用零填充把组尾对齐到 4 KiB，下一次提交不必重写上一组的尾页（减少物理写入字节）。
- **列编码（显式 Little-Endian）**：列数 `u16` + 各列 `tag`（`0 Null / 1 BigInt / 2 Varchar / 3 Vector`）及内容。
- **内存镜像（列式）**：表在内存预算内时，全部存活行常驻一份列式镜像 `MemTable`：
  - 向量列：按 1 MiB 定长块连续存放的 `f32`（不搬移、无逐行分配）；
  - 字符串列：追加式字节池 + 自适应 1-byte 标签 `tags`（当列内唯一字符串数 ≤ 254 时自动启用字典去重编码，相同字符串共享池内偏移且等值过滤直接按 1-byte 字典码精确匹配；超过 254 时自动切换为 1-byte 非零哈希指纹预筛 + 字节校验）；
  - 整数列：定长数组；`row_id → slot` 采用紧凑密集数组 `SlotMap`（4 B/行，稀疏 ID 自动回退哈希表）配合 `主键 → row_id` 哈希表。
  - 写入成功落盘后立即用 `posix_fadvise(DONTNEED)` 释放数据文件的页缓存：行已在内存镜像中，文件不会被再读，避免同一份数据在容器里占两份内存。
- **超内存预算的表（磁盘模式）**：内存预算取容器内存上限（cgroup `memory.max` / `memory.limit_in_bytes`）的 1/4、上限 512 MiB。超过预算的表只在堆上保留 `row_id → (偏移, 长度)` 与主键索引，查询时顺序流式扫描数据文件（选择性解码）或 `pread` 单行，不依赖全量载入内存。

## 2. 向量检索与索引方案

`exact` 与 `ann` 两种模式返回完全相同的**精确** TopK（Recall = 1.0），排序键为 `(距离, 主键, row_id)`，先过滤后取 TopK。

- **向量索引 = 7-bit 标量量化下界码（flat SQ）**。每个分量映射到 `floor((x - lo)/step)` 并截断到 `0..=127`。对落在格子 `ca < cb` 的两个值，真实差不小于 `(cb - ca - 1)·step`，所以 `Σ max(0, |ca - cb| - 1)² · step²` 是真实平方距离的**下界**（截断只会让边界格更大，下界仍成立；`step` 还预先扣除了单精度计算格边界的舍入误差）。
- **三遍扫描（均为自研 AVX2 内核，运行时检测，带标量回退）**：
  1. 对所有候选行计算整数下界（`subs/or/maddubs/madd`，每行 128 字节，约为 `f32` 向量的 1/4 内存带宽）；
  2. 取下界最小的 K 行做精确距离，得到一个"第 K 近距离"的上界；
  3. 只对下界不超过该上界的行（通常几十行）用双精度精确内核计算距离并排序。
  任何可能进入或并列 TopK 的行其下界必然不超过阈值，因此结果与全表双精度扫描逐位一致。
- **小表（< 1024 行）或数值范围不适合量化时**：单精度 AVX2/FMA 扫描选出"在舍入误差界内"的候选超集，再用双精度精排，同样是精确结果。
- **过滤**：`列 = 常量` 的合取在列上直接生成字节掩码（整数列逐值比较，字符串列哈希 + 字节校验），其余谓词逐行求值；掩码用 `movemask` 位迭代，只对命中行计算下界。
- **索引维护**：量化码在行写入内存镜像时同步更新（插入/更新/删除后立即一致）；显式事务内的未提交修改通过"屏蔽已修改行 + 合并写集"参与检索，回滚即丢弃写集。码表在首次检索时惰性建立，超出量化范围的分量过多时重建。
- `CREATE VECTOR INDEX` 记录索引元数据（名称、列、维度，可持久化、可回滚、重复创建报错）；量化码可随时由表数据重建，重启后在就绪前随数据装载恢复。

## 3. 事务处理、提交持久化与崩溃恢复

- **单事务写集**：未提交修改暂存在内存 `TxnWriteSet`；事务内的查询与向量检索合并读己之修改；语句失败不改写集，之前成功的语句仍可提交或回滚。
- **提交持久化**（响应发出前完成）：
  - 自动提交语句与单表事务：把该事务的组（行帧 + `Commit` 结束符）一次 `pwrite` 追加到表文件，再 `fdatasync`，成功后才更新内存镜像并应答。写失败则截回原长度，不留半个组。
  - 涉及多张表或 DDL 的事务：各表的组以 `Pending(txn)` 结束并分别 `fdatasync`，最后向 `/data/wal/wal_<seq>.log` 追加该事务的 `Begin + DDL 记录 + Commit` 并 `fdatasync`——WAL 中的提交记录是唯一提交点；提交点之前失败则把各表文件截回原长度。
  - `MVDB_SYNC` 环境变量可选 `full`（默认，`fdatasync`）/ `range`（`sync_file_range` 写入并等待，不强制文件系统日志提交）/ `off`。默认值满足断电级持久化；后两者只在题目声明的"进程被强杀"模型下成立，默认不启用。
- **恢复（幂等，可在恢复中途被再次强杀）**：
  1. 读取带 CRC 的 `checkpoint.meta`（表结构、代际、检查点时的文件长度、WAL 起点）；
  2. 扫描检查点之后的 WAL，截掉撕裂尾部，得到已提交事务号集合与其 DDL；
  3. 逐表顺序扫描数据文件重建内存状态：`Commit` 组直接生效；`Pending(txn)` 组仅当位于检查点长度之内或 `txn` 在 WAL 中有提交记录时生效；遇到第一个不成立的组、残缺帧或 CRC 错误即把文件截断到上一组末尾；
  4. 删除不属于任何已提交表的数据文件。恢复不依赖上一次恢复是否完成。
- **检查点与压缩**：死帧超过一半且文件 > 8 MiB 时把存活行重写到新代际文件（临时文件 → `fsync` → `rename` → 目录 `fsync`），再原子替换 `checkpoint.meta`、轮转 WAL、删除旧文件。正常关闭只回滚未提交事务；所有已应答的提交此前都已落盘，关闭时无需补写。

## 4. 已实现功能与已知限制

- **已实现**：`CREATE TABLE`（`BIGINT PRIMARY KEY`、`VARCHAR(n)`、`VECTOR(d)`）、`CREATE VECTOR INDEX`、`INSERT`（单行/多行/指定列）、`SELECT`（`*`/别名/`L2_DISTANCE`）、`WHERE`（`=, !=, <>, <, <=, >, >=, AND, OR, NOT, IS [NOT] NULL, BETWEEN, IN`）、`ORDER BY`、`LIMIT`、`UPDATE`、`DELETE`、`BEGIN`/`COMMIT`/`ROLLBACK`、精确 TopK（两种模式）、崩溃恢复、JSONL STDIO 协议与 Docker 封装。
- **已知限制**：
  - 单机单客户端单事务，不支持并发控制；
  - 不支持 `JOIN`、聚合、子查询、`ALTER TABLE`、`DROP TABLE`、`GROUP BY`/`HAVING`/`OFFSET`，返回 `unsupported_sql`；
  - 磁盘模式下每行仍有约数十字节的常驻元数据（位置表与主键索引）；
  - 检索始终是精确扫描（量化下界过滤 + 精排），复杂度随行数线性增长，面向本题规模设计。
  - 请求读取在两次请求之间会短暂轮询标准输入（默认最多 2 ms，`MVDB_SPIN_US` 可调，`0` 关闭），之后才阻塞等待。

## 5. 本地验证记录摘要

- `cargo test`：16 个用例通过（SQL 语义、Unicode/大整数、重启与压缩、距离内核等价性、索引维护、事务原子性、未提交/撕裂尾部故障注入、多表事务原子性、协议端到端）。
- 官方 `protocol_check/run.py --image`：握手与 20/20 公开用例通过（`--read-only --network=none --cpus=2 --memory=2g --cap-drop=ALL`）。
- 差分模糊测试：随机 SQL 流（多行插入、更新、删除、事务、非法向量、各种过滤与排序、TopK、正常重启与 `SIGKILL`）同时发给上一版与本版，逐条比较响应；内存模式、磁盘模式（预算设为 0）与触发压缩的大数据场景均无差异。
- 崩溃测试：在提交过程中、恢复过程中随机 `SIGKILL`，校验已应答批次全部存在、在途批次要么完整要么不存在、多表事务不出现只生效一半的情况。
- 资源测试：`--memory=128m` 容器写入 12 万行 128 维（约 66 MiB 数据），自动转入磁盘模式，查询结果与暴力真值一致，重启后行数正确。
